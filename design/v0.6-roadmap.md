# friendo v0.6 — roadmap

> **Status: scoped 2026-09-25, not started.** Scoped the day v0.5 was readied for its tag,
> from the shipped surface (personas, members-only pages, the calendar + RSVP, declared
> fields, feature switches) and four decisions put to the user. Builds on
> [v0.5-roadmap.md](v0.5-roadmap.md), [calendar-plan.md](calendar-plan.md) and
> [auth-permissions.md](auth-permissions.md).

**Scope theme: a social graph for a site's members, built the friendo way.** A group is a
post with members, the way an event is a post with a `when`. Everything is a row in the
site's own database, travels with the folder, and shows up in templates as filters and
`record.*` relations and on the page as `<friendo-*>` tags.

## Where things stand at v0.5

| Piece | Now |
|---|---|
| Identity | `users` are accounts; `authors` are the public personas (one account → many, `default_author_id`). Every community row — comments, reactions, messages, RSVPs — keys on `author_id`. |
| Profiles | An author is `name`, `email`, `avatar`, `role`. No `data`, no slug, no public page. The persona switcher edits name + avatar only. |
| Relationships | None. |
| Groups | None. `{% members only if … %}` takes an expression tail that was reserved for `user.groups` ([renderer/gate.go](../runtime/go/renderer/gate.go)); `[access]` gates paths by role only. |
| Events | `rsvps` hold one answer per member per occurrence (`going` / `maybe` / `no`). Nobody can be *asked*. |
| Reaching a member | The OTP email is the only outbound mail. Nothing in-page tells a member anything happened. |
| Switches | `comments reactions polls rsvp locations chats`. Off = API 403 `off: true`, tag renders nothing, templates see empty. |
| Declared fields | `[content.<type>.fields]` drives the admin's table + form and validates on save; the API stays open. |

## The four decisions

1. **One-way follow; friends are mutual follows.** One table, one word. A friend is derived
   (`a follows b and b follows a`), never stored twice. *Why:* one obvious concept for
   novices; an approval flow needs notifications to feel finished, and those come later.
   *Declined:* request-and-accept friends; both models from day one.
2. **The graph is per site.** Follows, groups, profiles are rows in the site DB; they sync on
   `push`/`pull` and export like RSVPs. A network account is just how you sign in. *Why:* a
   site is a folder; self-hosting parity. *Declined:* a network-wide graph.
3. **Notifications are in-page only in 0.6.** A member sees invites and requests when they
   visit; no email beyond the OTP. Email (immediate or digest) is a later release. *Why:*
   cheaper, and the in-page inbox is the piece every social feature needs first.
4. **Groups are a flexible built-in content type.** Members can create them when a setting
   allows; a group's moderators control generic settings in its `data` (public/private, how
   to join, and whatever the site declares); and because it's a built-in rather than
   something a developer assembles, friendo ships the filters, components and gates for it.
   The user's framing: "basically a content type that a developer could in theory build out
   themselves but it'd just be really complicated."

## Names (proposed)

| Thing | Name |
|---|---|
| Group record | a post in the **`groups`** collection; settings live in its `data` (`visibility: public \| members \| private`, `join: open \| request \| invite`) plus any `[content.groups.fields]` the site declares |
| Membership | table `memberships` (`group_id`, `author_id`, `role: moderator \| member`, `status: member \| requested \| invited`), migration `0016` |
| Follow | table `follows` (`follower_id`, `followee_id`), unique pair, migration `0015` |
| Profile | `authors` gain `slug`, `bio`, `data` (migration `0015`); `[profiles] fields` in `friendo.toml` declares the rest |
| Notification | table `notifications` (`author_id`, `kind`, `target_type`, `target_id`, `actor_id`, `read`), migration `0017` |
| Event invitation | an `rsvps` row with `answer = "invited"` — the existing per-occurrence key, no new table |
| Switches | `follows`, `groups` join the feature list (default on); `notifications` is implied by either |
| Settings | `social.member_groups` (members may create groups, default **off**); `social.profiles` (`public` \| `members`, default `members`) |
| Template context | `user.groups` (slugs), `user.following`, `user.followers`, `user.friends` |
| Relations | `record.members` on a group; `record.groups`, `record.followers`, `record.following` on a profile; `record.invited` on an event |
| Filters | `in_group "slug"`, `by_following` (posts by people you follow), `following`, `followers` |
| Gate sugar | `{% group "board" only %}` ≡ `{% members only if "board" in user.groups %}`; `[access] groups = { "/board/*" = "board" }` |
| SDK tags | `<friendo-profile>`, `<friendo-follow>`, `<friendo-group>` (join / leave / members / settings for moderators), `<friendo-groups>` (list + create), `<friendo-inbox>` plus a badge in `<friendo-auth>`, `<friendo-invite>` on an event |
| Pages | `pages/members/[slug].html`, `pages/groups/index.html`, `pages/groups/[slug].html`, scaffolded by `friendo init` |
| REST | `/_/api/members`, `/_/api/members/:slug`, `/_/api/follows`, `/_/api/groups/:id/members`, `/_/api/me/notifications`, `/_/api/posts/:id/invites` |

## Tier A — profiles

- `authors` gain `slug` (unique per site, derived from the name, editable), `bio`, and a
  `data` JSON column — the same lever posts got in `0003`. A `[profiles] fields` block in
  `friendo.toml` declares the rest, reusing the declared-fields machinery so the admin's
  Members screen and the persona editor lay themselves out from it.
- A public profile page at `/members/<slug>` rendered from `pages/members/[slug].html`
  (scaffolded), with `record` = the profile, `record.posts`, `record.comments`. Visibility
  follows `social.profiles`; a `members` default means a signed-out visitor sees the
  site's sign-in page in place, exactly like a gated page.
- `<friendo-profile>` shows a profile (own = editable); `GET/PUT /_/api/me/personas/:id`
  grows to cover the new columns. Profiles sync and export (public ones) like authors do.

## Tier B — follows

- `follows` + `POST/DELETE /_/api/follows` (member, toggle, rate-limited through
  `rate_limits`). `user.following` / `user.followers` / `user.friends` in the context;
  `record.followers` / `record.following` on a profile; the `by_following` filter for a
  "people I follow" feed. `<friendo-follow author="…">` is a toggle button with counts.
- Sync + export: follows travel on `push --users`; static export writes nothing about them.

## Tier C — groups

- The `groups` collection is built in the way `events` is: `friendo init` scaffolds
  `pages/groups/`, the admin lists it, and its records take the declared fields. Creating
  a group makes the creator its first moderator. `social.member_groups` decides whether
  members may create; owners/admins always can.
- `memberships`: join rules read from the group's `data.join` (`open` joins at once,
  `request` writes `requested`, `invite` only moderators add); moderators approve, remove,
  promote. `record.members` on the group; `user.groups` in the context — which makes
  `{% members only if "board" in user.groups %}` work with **no grammar change**, plus the
  `{% group "…" only %}` sugar and `[access] groups`.
- Visibility: `public` groups render for everyone, `members` for signed-in members,
  `private` only for members of the group (its page, members list and posts).
- A group owns things by reference, not by new tables: an event or post with `group: board`
  in its front matter belongs to it (`in_group "board"` filter; `/calendar.ics?group=board`
  and `/calendar.json?group=…` filter the feeds); a group's chat is a chat named for it (`chat-id="group-{{ record.slug }}"` — pages register the chats they name).
- `<friendo-group>` (join / leave / request / member list / moderator settings) and
  `<friendo-groups>` (list + create when allowed). Admin: a Members tab on a group record.

## Tier D — in-page notifications

- `notifications` rows are written by the things above: a follow, a join request (to
  moderators), an invite (to the member), an event invitation, and a comment on your post.
  `GET /_/api/me/notifications`, `PUT …/:id/read`, `PUT …/read-all`.
- `<friendo-inbox>` lists them; `<friendo-auth>` shows an unread badge. `user.unread` in
  the context. No email in 0.6; the table is shaped so a digest can read it later.

## Tier E — event invitations

- `POST /_/api/posts/:id/invites` (organizer = the event's author, editors and up) takes a
  list of member slugs, a group slug, or `followers`; each becomes an `rsvps` row with
  `answer = "invited"` for the next occurrence (or a named one), and a notification.
- `<friendo-rsvp>` shows the invited state and lets the member answer; `record.invited`
  joins `record.rsvps`; the Attendees screen and CSV show invited-but-unanswered.

## Deferred (named so the next release starts from here)

- **Email notifications** — immediate or daily digest per member, via the Resend seam.
- **Blocking / muting**, and who can see the follow graph beyond the counts.
- **Direct messages** — `chats.kind = "dm"` is the obvious home; not in 0.6.
- **Network-wide discovery** — the graph stays per site (decision 2).
- **Slots** — still deferred from the calendar plan.

## Open questions (settle before Tier A starts)

1. Should `authors` themselves become records in a `members` collection, so the admin table,
   declared fields, `record.*` and sync all apply for free? It's the bigger refactor but
   removes a parallel path. Decide before adding `data` to `authors`.
2. Default for existing sites when the binary upgrades: `groups` and `follows` on (like every
   other switch) with nothing created, or off until the owner turns them on?
3. Is a `members` profile visibility the right default for a personal blog's authors? The
   Personal / Community / Blog presets could set it.
4. Ordering: Tier D (inbox) could land before Tier C so join requests are visible from day one.
