# friendo v0.5 — roadmap

> **Status: shipped.** Scoped 2026-09-24, the same day v0.4.0 was tagged, from a read of the
> whole codebase against three questions: why does sign-in still need a password anywhere,
> what does a site owner or network operator actually get in a browser, and how does a
> network put a real site at its own front door. Implemented in four tiers, each green on
> `go test ./...` and the Playwright browser checks. Builds on
> [v0.4-roadmap.md](v0.4-roadmap.md) and [network-accounts.md](network-accounts.md).

**Scope theme: make sign-in one obvious thing, and make the network self-service end to
end — with the network's own UI built the friendo way (a home site + `<friendo-*>` tags).**

## Where things stood at v0.4

| Piece | Then |
|---|---|
| Sign-in | The server accepted an emailed code for *any* role, but every door an owner walked through demanded a password: first-run setup (API, SPA, CLI), the admin login screen, adding a user, CLI push/pull once a session expired. Self-service owners were created with a random bcrypt password and could not sign in to their own admin from a browser at all. |
| Bugs | `push/pull --users` blanked every password (`ListUsers` never selected the hash; the upsert overwrote with `''`). Operator-provisioned sites had no owner, so their setup screen was open to whoever arrived first. `/migrate` was unauthenticated. The network's OTP echo turned on for any non-empty value and ignored whether email was configured. Site and network handled email case differently. No cap on wrong code guesses. |
| Tenant UI | None. A non-operator signing in at the apex was turned away. Sites, quota and domains were CLI-only; `GET /api/account/sites` had no caller. |
| Operator UI | One server-rendered Go-template page with inline CSS. It could not add or verify domains, revoke operator, set an invite's expiry, or prune invites. Off the box, the CLI only covered provision/list/destroy. |
| Apex | Hard-wired to the operator login. No landing page, no way to mount a site there, `www` an ordinary claimable tenant, nothing reserving `docs`/`api`/`origin`. |
| Docs | No automated (or evident) publish; four pages still said "both runtimes"; a nonexistent `truncate` filter in the README and docs; no pages for custom domains, running a network, self-hosting, channels. |

## The eight decisions

Each was put to the user as a choice; the option taken is recorded with the reason.

1. **Email code by default, password opt-in.** A per-site setting, off by default. *Why:* one
   obvious way in for novices; the server already accepted codes for every role.
2. **`friendo serve` opens the admin with no sign-in on localhost** (same-machine request, a
   localhost `Host`, no proxy header, no email provider). *Why:* there'd be nowhere to send a
   code; a site on your own laptop is yours. `--require-login` forces the screens.
3. **The apex serves an operator-chosen home site.** The network's default pages
   (`/login`, `/activate`, `/account`, `/network`) are shells; **a home-site page at the same
   path intentionally takes over**; `/api/*` is always the network's; `www` → 301. *Why:* the
   user's own framing — "the network pages could be loaded exactly like a normal friendo site,
   and we could just build web components for the account/console things that get dropped into
   the www site's templates. That might be the most friendo-y way." The "separate SPA on a
   reserved subdomain" and the "shadow reserved paths, no override" variants were both offered
   and declined.
4. **Reserved subdomains** refused for self-service; operators provision them on purpose.
5. **Network UI as SDK Web Components**, not a second SPA: `<friendo-account>`,
   `<friendo-console>`, `<friendo-activate>`. The Go-template console retired.
6. **Browser "Open admin"** from the account page into a site's `/_/`.
7. **`www/` landing site in the repo** as friendo.world's first home site; `www/` and `docs/`
   published **manually** (`npm run deploy:www|docs`). CI deploy was offered and declined.
8. **No operator support-access into tenant sites.** Operators keep lifecycle powers only; the
   "Open admin" link is owner-only, operators included.

## Names

| Thing | Name |
|---|---|
| Password setting | `access.password_login` (default `false`); `[settings] password_login`; Settings card **Signing in**, toggle **Allow signing in with a password** |
| Home-site setting | `network_settings.home_site`; `friendo network home <sub>` / `--clear` / (show) |
| Network cookie | `friendo_account` (Path `/`, Lax, 30 days) — replaced `friendo_operator` |
| SDK tags | `<friendo-account>`, `<friendo-console>`, `<friendo-activate code="…">` |
| Default pages | `/login` and `/account` → account; `/network` → console; `/activate` → activate |
| Serve flag | `friendo serve --require-login` (env `FRIENDO_REQUIRE_LOGIN=1`); `--open-admin` kept |
| Site SSO landing | `GET https://<sub>.<base>/_/sso?code=…` (dispatcher intercept, before the site) |
| Reserved subdomains | `www api admin mail origin network console account login activate docs static cdn` |
| New CLI | `friendo open-admin [sub]`; `friendo network home`; `--owner` on `provision`/`network deploy` |

## Tier A — sign-in normalised, bugs closed

- `GET /_/api/setup` reports `passwordLogin` + `emailConfigured`; `POST /setup/request-code`
  emails (and always logs) a setup code keyed on the email itself; `POST /setup` takes
  `{code}` or `{password}`. **No owner row exists until the code verifies.**
- **A password at setup is itself the opt-in**: it turns `access.password_login` on. This is a
  deliberate softening of the plan's "password branch only when the setting is on": an older
  CLI only knows the password shape, and "I set a password, so I can use it" is the intuitive
  rule. The SPA and CLI still default to the code.
- `POST /auth/login` → 403 with a plain message while the setting is off. `verify-code` caps
  wrong guesses (5 / 15 min, the login lockout). `POST /users` takes no password (code-only
  account) unless one is given. `POST /migrate` is gated on the legacy admin password — it runs
  before any owner exists, so nothing else can gate it.
- Migration `0012` seeds the setting ON wherever a real password exists, so an upgrade never
  locks anyone out. Caveat: pre-0.5 tenant owners carry a random hash from the old
  `ensureOwnerUser`, so they're seeded ON too — harmless (nobody knows that password; the owner
  can switch it off), and A stops creating such rows: network-made owners are code-only.
- `ListUsers` selects the hash; the push upsert keeps an existing hash when the incoming one is
  blank (defends against old CLIs); `auth_methods` is written truthfully. Emails are
  lowercased at the boundary. One shared echo rule (`email.EchoEnabled`: explicit flag **and**
  no provider) for site and network.
- The localhost open rule lives in `admin.GetSessionUser`, set only by `server.Start` — never by
  `BuildSiteHandler`, so a site served by a network is unaffected. Two refinements found by the
  browser checks: a **real session always wins** (a member who signed in on localhost is that
  member, not the open-mode owner), and open mode applies **only to the admin UI's own calls**
  (the SPA sends `X-Friendo-Admin: 1`; the site's `<friendo-*>` tags don't), so a visitor on
  localhost is still a visitor and community features test the way they'll behave for real.
- SPA: code-first login/setup with the dev code prefilled, "Use a password instead" only when
  allowed, password field on the user form only when allowed, a **Signing in** settings card,
  the legacy password on the migrate screen. CLI: `SetupRequestCode`/`SetupWithCode`/
  `RequestCode`/`VerifyCode`; `authenticateSite` branches on what the site reports (absent →
  an older site → password, as before).

## Tier B — the apex is a home site; one API for every operator lever

- Dispatcher order: `www` → 301 (except a www site's own `/_/…`, so `friendo deploy www` and
  its SSO landing keep working); custom domains as before; apex: `/api/*` → network, else home
  site if set — **including the default pages when the home site defines that page** (a
  `HasPage` matcher on `server.BuiltSite`) — else the network's default page, else the site;
  any subdomain: `/_/sso` intercept → suspended check → site. The old apex site listing (it
  leaked tenant names) is gone; the landing lists nothing.
- Sessions: cookie **or** Bearer on every `/api/*` route (`accountFromRequest`). Non-operators
  get sessions; only `/api/network/*` checks the capability. Browser sign-in is JSON
  (`/api/auth/request-code|verify-code|logout`), first-operator bootstrap included; device
  approval is `POST /api/auth/device/approve` from a signed-in browser. Network OTP gained a
  resend window and a wrong-guess cap (`account_otp.attempts`, added in place).
- `operatorapi.go`: `GET /api/network`, `PUT /api/network/settings` (signups, default quota,
  home site), sites list/suspend/resume/owner, accounts list/suspend/resume/signout/quota,
  invites list/create(with days, or operator)/revoke/prune, operators grant/revoke (never
  yourself), domains list/add/verify/remove on any site. `POST /api/sites` (kept) now links an
  owner — the acting operator or a named email — **fixing ownerless sites**; destroy drops the
  owner row and clears `home_site` if it pointed there. Suspending an account no longer revokes
  its sessions: `ValidateSession` already refuses them, and leaving the token in place is what
  lets the person see *"suspended — contact the operator"* rather than a bare "sign in again".
- Every `friendo network …` subcommand gained the `--network` branch; `friendo network home`
  is new; on-box `provision` takes `--owner` (default `FRIENDO_OPERATOR_EMAIL`, warns if none).

## Tier C — components, Open admin, console retired

- `<friendo-account>`: sign-in (dev code prefilled), my sites with address / hold status /
  domains, **Open admin**, a domains panel (add → DNS table, check & go live, disconnect), new
  site with "n of m used" and API messages shown verbatim. `<friendo-console>`: every section
  above plus **Home site**. `<friendo-activate code>`: sign in if needed, then approve. One
  shared sign-in painter; a `NetworkElement` base that re-renders on `friendo:account`.
- `POST /api/account/sites/{sub}/admin-link` mints the site session (refactored
  `mintSiteSession`, shared with `/api/sso/exchange`), parks it behind a one-time code
  (in-process `sync.Map`, 60 s) and returns the site's `/_/sso?code=` URL with the scheme and
  port the apex was reached on. A wrong-site redemption doesn't burn the code; expiry does.
  The dispatcher sets `friendo_session` via the exported `api.SetSessionCookie` (same
  attributes as a normal login) and lands on `/_/`; anything else → `/_/?error=sso`, which the
  SPA's banner (once a leftover from the old platform) now describes truthfully.
- `apex.go` serves the four shells, `/friendo.js`, the landing, and JSON 404s under `/api/`.
  `console.go` (templates + form handlers + `friendo_operator`) is deleted.
- Cookie note: `friendo_session` (Path `/_/`) and `friendo_account` (Path `/`) coexist on the
  apex host, so a home page can carry `<friendo-auth>` and `<friendo-account>` together.
  SameSite: the SSO landing is a top-level navigation from the same site
  (`friendo.world` ↔ `sub.friendo.world`), which Chromium and Firefox treat as same-site for a
  Strict cookie. Verified in Chromium by the Playwright walk; **Safari is unverified** — if it
  drops the cookie, relax that one cookie to Lax. *(Superseded by Tier E: the cookie is now
  Lax and site-wide.)*

## Tier D — landing, docs, records

- `www/`: layout, index (hero, install one-liner, four cards, "how it feels"), **`pages/account.html`
  as the worked example of taking over a default page**, 404, stylesheet with `::part()` rules
  for the component. `friendo.toml` targets `https://www.friendo.world`.
- Docs: stale "both runtimes" passages fixed; `truncate` → `truncatechars`; `push --settings`
  removed; folder trees gained `content/`; auth page rewritten around the code; new **Hosting**
  group (self-host a site, run a network, custom domains, your network account) and Concepts
  pages for channels and maps, plus static export; CLI reference updated; `phase-3-community.md`
  moved to `design/` (it was a design log sitting in user docs).
- Scripts: `npm run deploy:www`, `npm run deploy:docs`. Both names are reserved, so the
  publishing account must be an operator. One-time on friendo.world:
  `friendo network home www --network https://friendo.world`.

## Found while publishing the docs: routes were frozen at first request

Redeploying `docs/` to friendo.world left every article a 404 while the sidebar listed
all of them. Cause: a site's route table was built once, when its handler was first
built — and `friendo deploy` builds that handler by hitting the site's push API *before*
the templates it's pushing exist on disk, so a dynamic page arriving in the push
(`pages/docs/[slug].html`) never routed until the process restarted. `friendo serve` had
the same gap: its watcher only triggered live-reload. Now the route table is live
(`server.routeTable`): a templates push calls `BuiltSite.Reload` through a new
`onTemplatesChanged` hook on `admin.Mount`/`api.Mount`, and the dev watcher reloads on any
`pages/` change. Reproduced and pinned by `runtime/go/network/pushed_routes_test.go`; the
live site needs the new binary (a restart alone would also have cleared it).

## Tier E — members-only pages

Added after the tag was cut, on the user's request ("auth gated routes"), with three
choices put to them: the tag's spelling, what a blocked visitor sees, and whether
`friendo.toml` should gate whole paths.

- **`{% members only %}`** (and `contributors/editors/admins/owners only`), chosen over
  `{% require member %}` and over page front matter. The user asked that it leave room for
  filtering by profile attributes and a future **groups** feature, so the tag takes an
  optional `if <expression>` tail evaluated against the template context — when groups
  add `user.groups`, `{% members only if "book-club" in user.groups %}` works with no new
  grammar (an `of "…"` sugar can be added as pure parser sugar later).
- **Blocked visitors see the sign-in page in place** at the same URL (401 signed out, 403
  otherwise), rendering `pages/login.html` — with a `gate` variable — or a built-in page
  with `<friendo-auth reload>`. No redirect, no `?next=`. The redirect variant was offered
  and declined.
- **`[access]` in friendo.toml** (`members_only = ["/members/*"]`, …), checked before
  routing so a 404 under a gated prefix doesn't reveal what exists.
- **Cookie:** `friendo_session` became site-wide (`Path=/`) and `SameSite=Lax` (a link from
  an email to a members-only page must carry the session; mutations are JSON
  POST/PUT/DELETE from `fetch`, which Lax never attaches cross-site). Logout clears both
  the new path and the legacy `/_/` one. `Vary: Cookie` on every page.
- **Why the tag is scanned, not just executed:** pongo2 runs only the root layout's
  document, so a tag at the top of a page that `extends` a layout would never execute. The
  route table pulls the tag text out of the file and compiles it alone; the same node also
  enforces when it sits in a layout or block. `RoleAtLeast` joined `RoleRank` in `data`.
- Static export skips gated pages and now uses the site's real name (it said "Friendo
  Site"); the 404 page got the real name too. `<friendo-auth reload>` is the general fix
  for pages that render `{{ user }}` server-side.
- Not done: per-record visibility, gating `/assets/*` uploads, viewer-relative
  `record.reactions`/`record.poll`, hot-reloading `friendo.toml`, and groups themselves.

## Coverage

`go test ./...`: Tier A (`tests/auth_code_test.go`, `users_sync_test.go`,
`migration_password_login_test.go`, `runtime/go/admin/admin_test.go`, the CLI round-trip's new
users leg); Tier B/C (`operatorapi_test.go`, `signin_test.go`, `apex_test.go` — home site,
override, www, Open-admin SSO — plus the reshaped device-auth test). `npm run test:sdk` adds
`tests/sdk-network.mjs`, which boots a real network and drives Chromium through sign-in →
console → home site → override → Open admin. The four older browser checks still pass against
the new sign-in code (they set up with a password, which is now the opt-in path). Tier E:
`tests/gate_test.go` + `gate_toml_test.go`, `renderer/gate_test.go`, `export/export_test.go`,
the route-table reload test, and `tests/sdk-gate.mjs` (built-in sign-in page → reload → viewer).

Still by hand before the tag: the Safari SSO cookie note above, and the live friendo.world
steps — `npm run deploy:www`, `npm run deploy:docs`, `friendo network home www`, then `/account`
→ Open admin over HTTPS with a real Resend code.

## Explicitly not in v0.5

- Operator support-access into tenant sites (decision 8). If it ever lands: explicit and
  audit-logged, never implicit.
- Storage quotas (still scoped-not-built from v0.4).
- The Phase 2 desktop editor.
- CI deploy of `docs/`/`www/` (offered; the user chose manual).
