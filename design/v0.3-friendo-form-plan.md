# v0.3 — `<friendo-form>` submission component (plan)

> **Status: not yet built.** This is the one v0.3-scoped item still outstanding — the
> `<friendo-form>` SDK component and its backend deltas. The plan below is current and
> targets the single Go runtime (`runtime/go`). See the repo `ROADMAP.md`.

An added scope item for [v0.3-roadmap.md](v0.3-roadmap.md), landing after Tiers 0–3.
It extends the SDK with one more piece of **intuitive markup**: a form an author
drops on a page that turns ordinary inputs — plus a few rich `<friendo-input>` types
— into a created post carrying arbitrary metadata, submitted straight from the
frontend.

This fits the release's consolidation thesis: no new backend primitive. The
create-a-post-with-metadata endpoint already ships — `POST
/_/api/collections/{collection}/records`, which accepts `slug/title/body/status`
plus an **arbitrary `data` JSON blob** ([api.go](../runtime/go/api/api.go#L315)) and
clamps status by capability via `recordStatusFor`. What's missing is the *front-of-house*: a novice can author a
post from a `content/` file, the admin SPA, or a CLI push — but not from a page on
their own site. `<friendo-form>` closes that, and (opt-in) opens the same path to
community members.

## What the author writes

```html
<script src="/friendo.js" defer></script>

<friendo-form collection="posts" redirect="/blog/{slug}">
  <input name="title" placeholder="Title" required />
  <friendo-input name="body" type="richtext" placeholder="Write your story…"></friendo-input>
  <friendo-input name="where" type="location"></friendo-input>
  <friendo-input name="cover" type="media" accept="image/*"></friendo-input>
  <friendo-input name="tags" type="tags"></friendo-input>
  <select name="mood"><option>calm</option><option>hyped</option></select>
  <button type="submit">Publish</button>
</friendo-form>
```

That's the whole contract. The author writes a normal form; the field **names**
decide where each value lands. No JS, no endpoint knowledge, no schema edit.

## Field-mapping convention (the novice-facing rule)

One rule, guessable without docs: **reserved names become post columns; every other
name becomes metadata under `data`.**

| Field name | Lands as |
|---|---|
| `title` | `post.title` |
| `body`  | `post.body` |
| `slug`  | `post.slug` (auto-derived from `title` if omitted) |
| `status`| requested status (clamped server-side by capability — see Auth) |
| *anything else* (`mood`, `tags`, `where`, `cover`…) | `data.<name>` → readable in templates as `{{ record.data.<name> }}` |

So the example above creates a post whose `data` is
`{ "where": {lat,lng}, "cover": "<asset-ref>", "tags": [...], "mood": "calm" }` — and
`{{ record.data.mood }}` / `{{ record.data.tags }}` render server-side today with no
extra wiring, because the `data` column already round-trips through the runtime.

## The component — a light-DOM controller, not a shadow widget

This is the one real departure from the existing SDK pattern, and it's deliberate.
`<friendo-auth>`/`<friendo-comments>`/etc. paint *their own* markup into a shadow
root. `<friendo-form>`'s inputs are **the author's own light-DOM children** — their
CSS must apply, their `<friendo-input>`s must be reachable, and a light-DOM
`<button type="submit">` can't drive a form living in a shadow tree (form controls
only associate within their own tree). So:

- `<friendo-form>` attaches **no shadow root**. It's a *controller*: on connect it
  wires submit (a `<button type="submit">`/`<button>` click, plus Enter) and, on
  submit, walks its `[name]` descendants — native `<input>/<textarea>/<select>` **and**
  `<friendo-input>` — to build the payload. The author styles their own inputs
  directly; `<friendo-form>` exposes only a thin status/error line via `part` for
  `::part()` (consistent with the rest of the SDK).
- It reuses the shared IIFE helpers already in [sdk/friendo.js](../sdk/friendo.js):
  `api()`, `jsonBody()`, `currentUser()`, the `friendo:auth` re-render event.

### Submit flow

1. **Gather** sync values: native fields by `name`; each non-media `<friendo-input>`
   via its `.value` getter. Split into reserved columns vs `data.*` by the table above.
   Derive `slug` from `title` if absent (dedupe server-side, see Open items).
2. **Create**: `POST /collections/{collection}/records` with `{title, body, slug,
   status, data}` → `{ record }` (201). One request covers everything except media.
3. **Media** (only if a `type="media"` input holds a pending file): upload to the new
   record via the existing media endpoint, then patch the returned asset ref into the
   record's `data` (`PUT /records/{id}`). Media is async and record-scoped, so it
   must follow creation — hence the two-step.
4. **Finish**: emit a `friendo:submitted` CustomEvent (`detail: { record }`), then
   either `redirect` (pattern with `{slug}`/`{id}` substitution) or reset + show a
   `part="status"` confirmation. Errors surface in `part="error"`.

## `<friendo-input>` — the rich-input contract

A labelled value-provider that `<friendo-form>` reads. Minimal contract: a `name`, a
`type`, and a **`.value` getter** (first cut reads `.value` directly; a later pass can
adopt `ElementInternals.setFormValue` for native form association). Each renders into
its own shadow root, `::part()`-styleable, matching the existing components.

First cut ships all four:

| `type` | Renders | `.value` shape | Notes |
|---|---|---|---|
| `richtext` | a `contenteditable` surface with a minimal toolbar | **markdown** string | Markdown, not HTML — flows through the existing `markdown` filter so it renders server-side; also the natural fit for the `body` column. |
| `location` | a click-to-pick map | `{ lat, lng }` | Reuses the **Leaflet + OSM** setup already lazy-loaded by `<friendo-map>` — no new dependency, loaded only on pages that use it. Can also feed the locations API when `name` targets it. |
| `media` | a file/image picker with preview | pending `File` → post-create asset ref | Uses the existing contributor+ media-upload endpoint; async, uploaded in submit step 3. |
| `tags` | a chip input | `string[]` | Pure light logic; lands in `data.<name>` as an array. |

Registered alongside the others in the `defs` map at the bottom of
[sdk/friendo.js](../sdk/friendo.js#L747); everything ships through `npm run sdk`
(never edit the generated copy).

## Auth & moderation — contributors author, members submit (opt-in)

Chosen model: **both, behind a per-site setting** — mirroring the existing
`content.require_approval` + comment-auto-approve machinery so there's nothing novel
to reason about.

- **Contributors+** (`content.create`) — allowed today, no change. `recordStatusFor`
  already does the right thing: publish-capable authors keep their requested status;
  others get `pending` when approval is required, else `published`.
- **Members** (passwordless community accounts) — gated by a new opt-in setting
  **`content.accept_submissions`** (bool, default `false`). When **on**, the create
  endpoint admits `member` and **forces `status = "pending"`** into the existing
  review queue, ignoring any requested publish. When **off**, members get `403` (as
  today). This is exactly the comment-submission shape: submit → pending → an
  editor approves via the queue that already exists (`GET /_/api/records?status=pending`
  + the publish endpoint).

### Backend delta (small, no migration)

`site_settings` is already a key/value store (migration `0006`), so this is a new key,
not a schema change:

1. Add setting `content.accept_submissions` to the settings surface + an admin-SPA
   toggle, alongside the existing comment auto-approve switch.
2. On `POST /collections/{c}/records`: if the caller lacks `content.create`, admit them
   only when `content.accept_submissions` is on **and** the caller is a signed-in
   member; then force `status = "pending"` for any non-`content.create` author. Keep the
   `403` otherwise.
3. Rate-limit submissions with the existing durable limiter, keyed `submission:<author>`
   (reuse of the comment/message limiter), so the opened surface can't be spammed.
4. Media uploads for member submissions: the media endpoint is `content.create` today.
   First cut keeps media as a **contributor+ affordance** (the `media` input hides/disables
   for members); relaxing it to "a member may attach media to their own pending post" is
   noted as a follow-on so the initial surface stays small.

Everything else — arbitrary `data`, status clamping, the review queue, publish — is
already built and covered by the test suite.

## Rendering & test coverage

- **No SSR of the form.** A create form is inherently interactive and auth-gated — the
  same client-side-by-design call the roadmap makes for chat and maps. The form is a
  `<friendo-*>` component; there's no no-JS story to render.
- **The created content already renders server-side.** Its `title/body` and any
  `data.*` fields read through the existing template relations and the `data` column —
  no new `attachRecordRelations` work. If a submission also drops a geo-tag via the
  `location` input, `<friendo-map>` already surfaces it.
- **Test coverage** rides the REST layer where the real logic lives (matching how the
  comment auto-approve toggle is tested), not the widget:
  - `scenarios.json`: member-submit **off** → 403; member-submit **on** → created
    `pending`; contributor → `draft`/`published` per approval; arbitrary `data`
    round-trips; the submission rate limit returns 429.
  - `npm run test:sdk` (Playwright): drive `<friendo-form>` with `title` + a `richtext`
    body + `location` + `tags`, submit, assert the record persisted with the expected
    `data` shape and status. Extend [tests/](../tests/) with an `sdk-form.mjs` harness
    like the existing `sdk-map`/`sdk-persona` ones.

## Phasing (each independently shippable)

- **A — core form.** `<friendo-form>` + native inputs + field-mapping + create-on-submit
  for contributors+. **Zero backend change.** This alone delivers "author a post from a
  page." MVP.
- **B — rich inputs.** `<friendo-input>` `richtext`, `tags`, `location` (sync values),
  then `media` (the async post-create upload step).
- **C — community submissions.** The `content.accept_submissions` setting + relaxed gate
  + forced-pending + admin toggle + submission rate limit + test scenarios.

## Open items / out of scope (first cut)

- **Slug collisions** — auto-suffix (`my-post-2`) on the server rather than reject, so a
  member submitting a common title never hits a wall. Decide the exact dedupe in
  implementation.
- **Edit via the form** — create-only for now; `PUT /records/{id}` already exists, so an
  `record-id` edit mode can follow without new backend.
- **Rich-text format** — markdown (recommended above) over HTML, for clean server-side
  rendering and body-column fit. If HTML is ever needed, it would require sanitize + a
  rendering decision.
- **Native form association** (`ElementInternals`) for `<friendo-input>` — a nicety over
  the first-cut `.value` reads; not required to ship.
- **Media for member submissions** — deferred follow-on (see backend delta #4).
