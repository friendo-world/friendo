# friendo v0.4 — roadmap

> **Status: in progress.** Scoped 2026-08-17, immediately after the v0.3.0 tag.
> **Tiers A, B and C are implemented**; what remains is the housekeeping and coverage
> items at the foot of this doc, and a live Cloudflare for SaaS run against a real
> zone (the client is covered against a stub API, not the real one). Builds on
> the shipped single-runtime pivot + network mode — see the repo
> [ROADMAP.md](../ROADMAP.md) and [network-accounts.md](network-accounts.md).

**Scope theme: make the network safe to open to real tenants.**

v0.3 was the consolidation release — it made the *site* surface solid (intuitive
markup for every feature, coverage past REST). v0.4 turns to the *network*: friendo.world
is live on network mode, but it is still an operator-shaped demo. Everything that keeps a
public sign-up list from costing the operator money or a support headache is missing:
there is no cap on what an account can create, account management stops at the console UI,
and a tenant cannot bring their own domain.

The desktop editor (Phase 2) stays deferred. It is the bigger novice-facing bet and an
independent track; opening the network is the thing blocking real users *today*.

## Where network mode actually stands

Grounding for the work below, from the code as of v0.3.0:

| Piece | Today |
|---|---|
| Site registry | folder-based — [`Registry`](../runtime/go/network/registry.go) walks the network root; a `Site` is `{Subdomain, Dir, Name}` |
| Ownership | `site_owners (subdomain PK, account_id)` in the accounts DB ([account.go](../runtime/go/network/account.go)) |
| Network config | `network_settings` key/value; **`signups`** (`open`/`invite`, default invite) is the only key |
| Routing | [`Dispatcher.subdomain`](../runtime/go/network/dispatcher.go) strips `.<baseDomain>` from the request host — the **only** host→site mapping |
| Auth | passwordless OTP + device-auth; `operator` is a capability on an account |
| Limits | site-count quota (default 3/account, per-account override, operators exempt) |
| Levers | account + site suspension, session revocation, expiring invites |

## Tier A — Quotas ✅ shipped

The smallest change that makes `signups = open` a survivable setting. Per the
network-accounts open items, first cut is a **site-count cap**; storage follows.

- **Default cap** as a `network_settings` key (`quota.sites_per_account`), operator-editable
  from the console + CLI, so there is no recompile to change it.
- **Per-account override** — an `account_quotas (account_id, sites)` row wins over the
  default, so the operator can lift the cap for one tenant without lifting it globally.
  Accounts holding `operator` are exempt.
- **Enforced at the claim path** — the self-service `POST /api/account/sites` counts
  `site_owners` for the account and refuses past the cap with a **clear, actionable 403**
  (not a bare error — the message is the only thing a novice sees).
- **Surfaced before the wall** — the console shows *used / allowed*, and `friendo deploy`
  prints the same when it fails, so hitting the cap is never a surprise.
- **Storage quota** is scoped but *decided, not built* here — accounting is not obvious once
  media lives in R2 rather than on the box. Decide whether it is measured (a periodic
  per-site walk) or metered (tracked at upload) before committing; the count cap ships first
  either way.

## Tier B — Accounts & signups management past the console UI ✅ shipped

Today the operator can toggle signups and mint invites in the console, and grant operator
from the CLI. The gaps are the ones that show up the first time something goes wrong.

- **`friendo network accounts`** — list accounts with their site counts and capabilities;
  the CLI counterpart to what the console shows.
- **Suspension** — suspend an account (blocks new sessions + new claims) and suspend a site
  (dispatcher serves a hold page instead of the tenant). This is the abuse lever that has
  no answer today short of `network destroy`, which is irreversible.
- **Session revocation** — drop an account's `account_sessions` rows, for the "I lost my
  laptop" case that passwordless auth otherwise has no answer to.
- **Invite lifecycle** — list, revoke, and expire invites, not just mint them.

### What shipped in A + B, and the calls made along the way

- **Quotas** — `quota.sites_per_account` (default **3**) in `network_settings`, an
  `account_quotas` override table, enforced in `createSite` before anything is
  provisioned. `0` means unlimited, so one integer column covers both. A refused claim
  returns 403 with `used`/`allowed` alongside the message; `GET /api/account/sites`
  carries the same numbers so the cap is visible *before* it's hit.
- **Suspension is immediate, not just prospective.** `ValidateSession` rejects a
  suspended account, so sessions issued *before* the suspension stop working too —
  otherwise an abuser keeps going for the 30-day session life. Suspending from the CLI
  also ends existing sessions and says how many.
- **Operators can't be suspended.** Guarded in `SuspendAccount`, because suspending the
  last operator would lock the network's owner out of their own network. `friendo network
  operator revoke` was added so the guard is actionable rather than a dead end.
- **Invites became real records.** An invite used to *be* a pre-created account, which is
  why it could never expire or be taken back. `invites (email, expires_at, created,
  invited_by)` now backs the signup gate (account exists **or** valid invite), with a
  14-day default TTL, revoke, and prune. Accounts pre-created the old way still sign in —
  covered by a regression test.
- **Site suspension stayed off the dispatcher's back.** `Dispatcher.SetSuspendedCheck`
  takes a function (like `SetDestroyer` already does) rather than an accounts handle, so
  the dispatcher keeps knowing nothing about accounts. The check runs before the handler
  cache, so suspend and resume both land on the next request.
- **Storage quota** is still scoped-not-built, and still needs the measured-vs-metered
  call below.

## Tier C — Custom domains ✅ implemented

The last item on the known-gaps list, and the biggest single piece of v0.4. A tenant
pointing `theirdomain.com` at their site touches routing, verification, and TLS.

**TLS decision: Cloudflare for SaaS.** Chosen over on-box ACME because the same
Cloudflare API relationship is what a future **domain-sales** feature would be built on
— buying a domain and connecting one want the same plumbing, and splitting them across
two providers would mean building it twice. Cloudflare validates ownership and issues
and renews the certificate, so the network process never handles TLS, which keeps its
current role unchanged.

**But it sits behind a provider seam**, the same shape as the existing email/Resend
sender. friendo is self-hostable; a self-hosted network has no Cloudflare for SaaS, and
requiring it would strand exactly the audience the single-runtime pivot was for. So
[domainprovider.go](../runtime/go/network/domainprovider.go) defines `DomainProvider`
with two implementations:

- **`CloudflareProvider`** — Custom Hostnames API. On when `FRIENDO_CF_API_TOKEN` +
  `FRIENDO_CF_ZONE_ID` are set. friendo.world's path. Covered against a stub API;
  **still needs a live run against a real zone**.
  - **HTTP validation by default** (`FRIENDO_CF_SSL_METHOD=txt` to override). Once the
    tenant's CNAME resolves, Cloudflare proves ownership and issues the certificate on
    its own — so the tenant adds **one record**, not three. The `txt` path is kept for
    pre-validating a domain before its live traffic moves, and surfaces both the
    ownership record *and* `ssl.validation_records` (the certificate challenge; showing
    only the former leaves a tenant waiting on a cert they were never told how to get).
  - **CNAME target and fallback origin are separate settings**, because Cloudflare treats
    them as separate things: `FRIENDO_CF_CNAME_TARGET` is what tenants point at,
    `FRIENDO_CF_FALLBACK_ORIGIN` is where Cloudflare forwards to. The target defaults to
    the origin, which is the common arrangement. An earlier cut conflated them under one
    name that did neither job properly.
  - **The fallback origin is set at boot** (`EnsureFallbackOrigin`), not by hand in the
    dashboard. It's read-then-write, so a matching origin isn't rewritten on every start.
    Skipping it makes every custom hostname validate and then 502 — the kind of setup step
    that gets missed once and costs an hour.
- **`DNSProvider`** — a TXT record the network checks itself, leaving TLS to whatever is
  already in front. The default, so a self-hosted network works unconfigured.

The rest is provider-independent:

- **Host mapping** — a `site_domains (domain PK, subdomain, verified, created)` table, and a
  `Dispatcher` lookup that falls back to it when the request host is *not* under `baseDomain`.
  This is the first time routing is not a pure string operation, so it needs the same LRU
  care the handler cache already gets.
- **Verification** — prove the tenant controls the domain (a TXT record, or a token served
  from a `.well-known` path) before serving it. Unverified domains must never route.
- **Tenant flow** — `friendo domain add theirdomain.com`, with the verification instructions
  printed in plain language, plus the equivalent in the console.
- **Coverage** — the dispatcher test gains custom-host cases; verification gets unit coverage.

### How it came out

- **Verification is one gate, whoever runs it.** `site_domains.verified` is the only thing
  routing consults, and only `VerifyDomain` sets it — the provider merely answers
  "ready?". So the hijack case (claim `someone-elses.com`, wait for its DNS to point here)
  is closed the same way under either provider.
- **The routing lookup is cached, positives and negatives alike** (30s TTL, 1024 entries,
  dropped wholesale past the cap). Stray internet traffic to unknown hosts is the common
  case and shouldn't hit SQLite each time. `Dispatcher.ForgetDomain` is called when a
  domain is verified or disconnected so those land immediately rather than after the TTL.
- **The dispatcher still knows nothing about accounts** — `SetDomainLookup` takes a
  function, matching `SetDestroyer` and `SetSuspendedCheck`.
- **Suspension applies to custom domains too**, and the hold page names the address the
  visitor actually typed rather than the internal subdomain.
- **Detach is best-effort.** A Cloudflare failure is logged but never blocks disconnecting
  a domain — a tenant must not be stuck because a third party is having a bad day.
- **`friendo domain` is a tenant command, not an operator one**: it authenticates with the
  same cached device-auth token `friendo deploy` uses, and defaults to the site in the
  current folder.

## Open policy decisions (settle before, not during)

1. **Operator support-access into tenant sites.** Still open from the single-runtime pivot.
   The default power boundary is *site lifecycle + resources, not site content*; the
   alternative is "operator implicitly owns every site." If support-access lands it must be
   **explicit and audit-logged**, never implicit. This gates any "help a tenant fix their
   site" workflow.
2. ~~**Storage quota accounting** — measured vs metered.~~ **Deferred past v0.4** — the
   site-count cap is what actually bounds cost today; revisit with real usage data to
   size it against.
3. ~~**Custom-domain TLS** — Cloudflare for SaaS vs on-box ACME.~~ **Settled: Cloudflare
   for SaaS**, behind a provider seam (see Tier C).

## Housekeeping carried in

- **Confirm Resend on friendo.world.** Email delivery is now the *only* login path — an OTP
  that does not arrive is a total lockout, and this has not been re-verified since the
  cutover. Worth a synthetic check rather than a one-time manual confirmation.
- The `/activate` page open item in [network-accounts.md](network-accounts.md) was stale — it
  shipped ([accountauth.go](../runtime/go/network/accountauth.go)) and has been pruned.

## Coverage gaps this release should close

From the [ROADMAP.md](../ROADMAP.md) testing section, the two areas still untested are both
network-mode ones this release touches anyway:

- the live `friendo deploy` device-auth path against a running network;
- the storage backend against a real S3/R2 endpoint (today only the in-process test double).

## Explicitly not in v0.4

- **Phase 2 desktop editor** — the largest bet; independent track; form factor (desktop vs
  in-browser) still undecided.
- **`pull --community` snapshots** — carried forward from the v0.3 deferral list.
