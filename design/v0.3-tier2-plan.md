# v0.3 Tier 2 — coverage past the REST API (execution plan)

> **Historical / superseded.** Pre-pivot execution plan. The features shipped, but the
> "both runtimes / parity" and Workers-for-Platforms framing is obsolete — friendo has
> unified on a single **Go runtime**. See [network-accounts.md](network-accounts.md)
> and the repo `ROADMAP.md`.

Sequenced plan for Tier 2 of [v0.3-roadmap.md](v0.3-roadmap.md): make the parity
guarantee *proven* through the **render layer** and the **CLI flow**, and harden the
**SQL statement splitter** — the three places the v0.2 harness doesn't reach.

## Starting point (verified in code)

- The 155-step harness ([scenarios.json](../tests/scenarios.json)) is **REST-only**;
  both runners are thin interpreters of the same request→assert format.
- Render coverage is an **edge-only smoke** (`renderCheck` in
  [edge-parity.mjs](../tests/edge-parity.mjs)) with a hardcoded expectation — the Go
  runner has **no** render check, so there is no true cross-runtime render *parity*.
- Both runtimes order a published collection `created DESC`, so fixtures with
  explicit `created` render in a deterministic, identical order.
- The Go render handler injects a live-reload `<script>` before `</body>`
  ([server.go](../runtime/go/server/server.go)) — an asymmetry vs edge, avoided by
  using **fragment templates** (no `</body>`).

## (A) Render-layer parity suite

- **Shared fixtures** — `tests/render-scenarios.json`: `[{name, template, records,
  expect}]`, `expect` the exact rendered fragment (a golden both engines must match).
- **Go driver** — extract `server.BuildSiteHandler(siteDir, db, openAdmin)` from
  `Start` (product value: the serve path becomes testable). `tests/render_test.go`
  writes each fixture's template to `pages/<name>.html`, inserts its records with
  explicit `created`, mounts the handler over `httptest`, GETs `/<name>`, asserts
  `body == expect`.
- **Edge driver** — replace `renderCheck` with a loop over the same fixtures: push
  template + records, GET the page, assert equal.
- **Fixtures target the divergence-prone core**: nested same-tag `for` + `forloop.*`
  (Counter/First/Last), autoescape of `< > & " '` (the `'` was the v0.2 edge gap),
  `if/elif/else`, and a representative filter set both engines implement.

## (B) SQL statement-splitter robustness

- `applyD1Schema` in [platform/worker.js](../platform/worker.js) splits on `;` and
  drops lines that *start* with `--` — but `schema.sql` opens with comment lines, so
  the first `CREATE TABLE` can be lost (the bug noted in the CfP-path audit). Align
  it with the robust line-by-line stripper in
  [migrations.js](../runtime/edge/migrations.js) `splitStatements`, and add a unit
  test over a comment-led multi-statement string.

## (C) CLI push/pull round-trip

- The deploy flow (`init → push → pull`) has no automated coverage. Add a focused Go
  test that boots the Go runtime over a temp site, pushes records + assets, pulls
  them back, and asserts the round-trip — the one flow exercised only by hand today.

## Verify

`npm test` (both runtimes, incl. the new render fixtures), the new splitter + CLI
tests, and a clean `go vet` / `node --check`.

## Out of scope (noted)

- Per-record **relation** rendering (comments/reactions/poll/gallery) in the render
  suite — verified by hand-driven diff in Tiers 0–1; folding it in needs dynamic
  single-record routes and is a follow-up once the fixture harness exists.
- Full CLI coverage of `deploy`/`redeploy`/`destroy` against live Cloudflare (the
  platform path) — stays a manual/live check.
