# friendo v0.9 — roadmap

> **Status: proposed 2026-09-30, not scheduled.** Comes after 0.7 and 0.8.
> - Source: a feasibility read of the code, prompted by the question "can a site be viewable
>   in Tor Browser at a `.onion` address, even when it's deployed to a network?"
> - Builds on [v0.4-roadmap.md](v0.4-roadmap.md) (custom domains, whose routing this reuses)
>   and [v0.5-roadmap.md](v0.5-roadmap.md) (the localhost open admin, which this must not
>   expose).
> - Code references are files and function names as of 2026-09-30. Re-check them before
>   building.

**Scope theme: onion addresses — a site readable in Tor Browser, from a laptop or a network.**
Whoever deploys a site can give it a `.onion` address alongside its network subdomain, or
serve one straight from `friendo serve`.

## Verdict

**Feasible, moderate effort (~1.5–2.5 weeks), and a good fit for friendo's architecture.**

- **Pure-Go Tor is not an option yet.** No pure-Go library can host an onion service safely.
- **Use [`cretz/bine`](https://github.com/cretz/bine) to drive a real `tor` program.** That's
  the standard approach. It's one small, CGO-free Go dependency, plus `tor` installed on the
  machine: `brew install tor` on a laptop, `apk add tor` in the Docker image.
- **The network is the easy half.** It already routes verified custom domains by Host header.
  An onion address is essentially a custom domain that is verified from the moment it's made.
- **Two security holes in `friendo serve` must be closed first.** See
  [Blockers](#blockers-fix-before-any-onion-ships).

## How onion services work (1-minute version)

- **The address is a key.** A v3 onion address (`<56 chars>.onion`) is derived from an
  ed25519 keypair. Whoever holds the private key *is* that address.
- **No DNS, no certificates.** Nobody issues the name and nothing is registered.
- **Tor only makes outbound connections.**
  - The machine running `tor` publishes a small "descriptor" into the Tor network and keeps a
    few outbound circuits open. Visitors meet it through those.
  - So there are no open ports, no Traefik and no Cloudflare, and it works behind NAT or a
    firewall.
- **Tor hands the app plain HTTP.** It forwards each visitor's connection to a local port
  (say `127.0.0.1:3000`), with `Host` set to the onion name.
- **No HTTPS needed.**
  - The connection is already end-to-end encrypted and authenticated by the address itself.
  - Tor Browser treats `http://*.onion` as a secure context and accepts `Secure` cookies
    there.
- **A clearnet site can advertise its onion.** An HTTPS response can send
  `Onion-Location: http://<addr>.onion/...`, and Tor Browser then shows a ".onion available"
  button.
- **Keeping the address means keeping the key.** Lose the key and the address is gone for
  good. Leak it and someone else can impersonate the site.

## Which Go package

| Option | Verdict |
|---|---|
| **[`cretz/bine`](https://github.com/cretz/bine)** (MIT) | **Use this.** See the notes below the table. |
| [`opd-ai/go-tor`](https://github.com/opd-ai/go-tor) | Pure-Go Tor, tiny project. Its README says **"NOT safe or production-ready"**. Its [bine wrapper](https://pkg.go.dev/github.com/opd-ai/go-tor/pkg/bine) still needs the `tor` binary to host onion services. |
| [`ipsn/go-libtor`](https://github.com/ipsn/go-libtor) (embeds tor via CGO) | **Archived Feb 2026.** It bundles Tor 0.3.5, long past end of life. |
| `cretz/tor-static` + `bine/process/embedded` | Needs CGO, which breaks the `CGO_ENABLED=0` builds in `.goreleaser.yaml` and the Dockerfile. friendo would also then own tracking Tor security releases. Not worth it. |
| Arti (the Tor Project's Rust rewrite) | Onion hosting is still experimental there. A possible sidecar one day; not Go. |

About bine:
- It controls a real `tor` process.
- The high-level API is [`tor.Start`](https://pkg.go.dev/github.com/cretz/bine/tor) then
  `t.Listen(ctx, &tor.ListenConf{Key, RemotePorts, NonAnonymous})`, which returns a
  `net.Listener` plus the onion ID.
- The low-level `control` package has `AddOnion` / `DelOnion`. A network with many onions
  needs this one.
- Its last tag is v0.2.0 (2021). That's fine: it speaks Tor's control protocol, which is
  stable. A maintained fork exists at `alexballas/bine`.

**Requiring `tor` to be installed is acceptable.**
- The network image gains one Dockerfile line: `apk add --no-cache tor`. Alpine 3.20 ships
  tor 0.4.8.
- On a laptop, friendo detects a missing `tor` and prints the install command for the OS.
- A friendlier later step: friendo downloads the Tor Project's "Expert Bundle" into
  `~/.friendo/tor/`. The same kind of download the `friendo upgrade` self-updater does in
  [cli/internal/upgrade](../cli/internal/upgrade/).

## What already fits (reuse, don't rebuild)

- **Handlers are plain `http.Handler`s.** `server.BuildSite`
  ([server.go](../runtime/go/server/server.go)) and the network `*Dispatcher`
  ([dispatcher.go](../runtime/go/network/dispatcher.go)) can be served on a second listener
  with `http.Serve(onionListener, h)`.
- **Custom-domain routing already exists.**
  - A host outside the base domain goes through `Dispatcher.resolveDomain` →
    `Accounts.SiteForDomain` ([domain.go](../runtime/go/network/domain.go)).
  - Only verified rows route.
  - `NormalizeDomain` already accepts a v3 onion name.
- **Links follow the request.** `{{ site.url }}`, calendar links and the `.ics` / `.json`
  feeds are built from the request's Host (`requestOrigin` in server.go, `baseURL` in
  [calendar/http.go](../runtime/go/calendar/http.go)). There's no configured site URL, so on
  the onion they come out as `http://<addr>.onion` for free.
- **The SDK uses relative URLs.** `/_/api`, and the chat streams are same-origin SSE.
- **Nothing redirects to https.** No http→https redirect, no HSTS header.
- **Sign-in emails carry a code, not a link** ([email/email.go](../runtime/go/email/email.go)).
  So there's no clearnet URL in them.
- **Suspension works unchanged.** The dispatcher's suspended check runs after domain
  resolution.

## Blockers (fix before any onion ships)

Tor connects to the app from `127.0.0.1`, and a Tor *client* can send any `Host` header it
likes. Tor Browser is well-behaved; a script isn't.

1. **Owner access from anyone on Tor (`friendo serve`).**
   - A request with `Host: localhost` and `X-Friendo-Admin: 1` passes `isLocalRequest`
     ([admin/admin.go](../runtime/go/admin/admin.go)).
   - `GetSessionUser` then returns the open-mode **owner**.
   - This is the default whenever no email provider is set.
2. **Sign-in codes echoed to anyone (`friendo serve`).**
   - With no email provider, `server.Start` sets `FRIENDO_OTP_ECHO=1`, which returns codes in
     API responses.
   - Anyone reaching the onion could sign in as any email, the owner's included.
3. **Rate limits are forgeable or shared.**
   - `clientIP` ([api/visitors.go](../runtime/go/api/visitors.go)) trusts `CF-Connecting-IP`
     and `X-Forwarded-For` whenever the peer is loopback. A Tor client can forge them.
   - Without those headers, every onion visitor lands in the same `127.0.0.1` bucket, so one
     abuser locks out all Tor visitors.
   - This matters most for the visitor features (anonymous posting, drop box).

**The fix for all three is a dedicated onion listener.**
- Onion traffic arrives only on that listener. Its `http.Server` wraps the handler in a small
  `onionOnly` middleware that:
  - strips `X-Forwarded-*`, `Forwarded` and `CF-Connecting-IP`;
  - marks the request context as "came via onion".
- `isLocalRequest` and `OpenLocally` answer false for onion requests. `localhost:3000` keeps
  its open admin for the owner.
- `clientIP` returns a dedicated `"onion"` bucket with its own limit.
- OTP echo is off whenever `--onion` is on. With no email provider, onion visitors just can't
  sign in, and friendo says so at startup.

## Design

### A. Laptop — `friendo serve --onion`

- **Flag:** `--onion` on `serve` ([cli/cmd/friendo/main.go](../cli/cmd/friendo/main.go)),
  with a `FRIENDO_ONION=1` fallback. Same pattern as `--require-login`.
- **Tor:** `server.Start` starts `tor` through a new `runtime/go/onion/` package. Tor's
  working directory is `<site>/data/tor/`.
- **Key:** kept at `<site>/data/onion.key`, so the address survives restarts.
  - Bundle export copies only `data/friendo.db`, so the key stays out of bundles.
  - The scaffold writes no `.gitignore` today. Add one covering `data/`.
- **Startup message:** "Your site is also at http://\<addr\>.onion (reachable while this
  computer is on)".
- **Normal (anonymous) onion mode.** The laptop's location stays hidden, as long as nothing
  else gives it away (see [What an onion does and doesn't give you](#what-an-onion-does-and-doesnt-give-you)).
- **Plumbing:** `Start` moves from `http.ListenAndServe` to `http.Server{}` + `Serve` on two
  listeners. That's the natural moment to add graceful shutdown, which nothing has today.

### B. Network — `friendo deploy --onion`

**Tor process**
- `friendo network serve` starts **one** `tor` at boot when `FRIENDO_TOR=1`, wired in
  [cli/cmd/friendo/network.go](../cli/cmd/friendo/network.go).
- Its data directory is `/data/tor`, on the existing volume, so restarts are quick.
- It runs in **single-onion mode** (`HiddenServiceSingleHopMode 1`,
  `HiddenServiceNonAnonymousMode 1`, `SocksPort 0`).
  - The server's location is public anyway, since it serves the same sites on clearnet.
  - This mode roughly halves latency for visitors.

**Routing**
- Every onion forwards to **one shared** local listener, served by `onionOnly(dispatcher)`.
- Onions are added and removed with bine's low-level `control.AddOnion` / `DelOnion`. The
  high-level `Listen` wants one listener per service.
- Requests arrive with `Host: <addr>.onion` and go through the existing custom-domain lookup.
- `onionOnly` refuses any Host that isn't a registered onion, so the onion can't be used to
  reach the apex's `/api/*`.

**Storage**
- A new `site_onions(subdomain PK, address UNIQUE, secret_key BLOB, created)` table in
  `accounts.db`, next to `site_domains` ([account.go](../runtime/go/network/account.go)).
  It's network-side and never pushed or pulled.
- Not `site_settings`: push, pull and export copy that whole table to the owner's machine.
- The dispatcher's `SetDomainLookup` closure checks `site_onions` for `*.onion` hosts.
- `AddDomain` refuses `.onion` names, so they never reach Cloudflare for SaaS.
  `attachDomain` always calls the provider.

**API and CLI**
- `POST` / `DELETE /api/account/sites/{sub}/onion`, modelled on the domain attach and detach
  handlers in [accountauth.go](../runtime/go/network/accountauth.go), with the same ownership
  check. `POST` does four things:
  1. generates a key;
  2. inserts the row;
  3. calls `AddOnion` on the live tor;
  4. returns the address.
- `RunNetworkDeploy` ([cli/internal/deploy/account.go](../cli/internal/deploy/account.go))
  gains `--onion`. After creating the site it calls the endpoint and prints the address.
- It has to be an API call because `friendo.toml` doesn't travel on deploy. The push handlers
  only accept `pages/`, `layouts/` and `assets/`.
- The onion address shows in `<friendo-account>`'s site list and in the operator console.

**Lifecycle**
- **At boot**, re-add every `site_onions` row. Nothing loads sites at startup today, so this
  is a new loop.
- **On destroy**, `DelOnion` and delete the row, via `OperatorAPI.SetDestroyer`.
  - Destroy already leaves `site_domains` rows behind; fix that alongside.
- **Changes go through the HTTP API**, as domain changes already do. On-box CLI commands run
  as separate processes and can't reach the running tor.

**Clearnet bonus**
- An `Onion-Location` header on HTTPS responses for sites that have an onion, set in the
  dispatcher.
- Tor Browser users who land on `sub.friendo.world` then get the ".onion available" button.

**Docker**
- `apk add --no-cache tor` in the Dockerfile. No port or Traefik changes.
- A section in [DEPLOY.md](../DEPLOY.md).

**Scale**
- Each onion keeps about three intro circuits and republishes its descriptor periodically.
- Hundreds per `tor` is fine. Beyond that, run several `tor` processes, as the Tor Project's
  Onionspray does.

### C. Onion *instead of* a subdomain (follow-up)

- **Every network site still has a subdomain internally.** It's the folder name and the key
  everything is filed under ([registry.go](../runtime/go/network/registry.go)).
- **So "onion-only" means the public pages don't answer on the clearnet subdomain.**
- **`/_/` has to stay reachable there.** `friendo deploy` pushes over HTTPS to
  `sub.friendo.world/_/api/push/*`. Pushing over Tor would need Tor on the deployer's machine
  too.
- **It's a small dispatcher check on top of B.** A random subdomain keeps the name from
  hinting at the site.
- **Recommendation: ship B first** (onion *alongside* the subdomain), then this.

## What an onion does and doesn't give you

State this honestly in the user docs.

**Does:**
- Tor users reach the site without exit nodes.
- Their visits are private end to end, and censorship is harder.
- The address proves it's authentic by itself.

**Doesn't, on a network:**
- **Hide the site from the operator.** The network holds the key and the content.
- **Hide who runs the site** once it also has a clearnet subdomain.

**On a laptop, hiding the location is possible but fragile:**
- The email provider (Resend) sees the server's IP.
- Serving the same site on clearnet ties the two together.

## Tor Browser caveats

**At the "Safest" level (no JavaScript), sites are read-only.**
- Pages are server-rendered, so reading works.
- Sign-in, posting, comments, RSVP and chat all need JS, because the API is JSON-only with no
  plain `<form>` fallback.
- Members-only pages render once signed in, but signing in needs JS.
- This fits "SSR where content earns it". HTML-form fallbacks would be separate, larger work.

**Three things still load from the clearnet** ([sdk/friendo.js](../sdk/friendo.js)):
- `<friendo-map>` loads Leaflet from unpkg.com.
- `<friendo-map>` loads its tiles from openstreetmap.org.
- The rich-text editor loads from esm.sh. It falls back to a Markdown textarea when that
  fails.

For maps, either offer self-hosted Leaflet plus a tile option, or document them as
"loads from clearnet".

**Live reload runs in production.**
- The live-reload script is injected into every page, even in network mode, because the
  dispatcher builds sites with `server.BuildSite`.
- It reloads the page whenever its event stream drops, and Tor circuits drop often.
- Worth fixing regardless of onions: only inject it under `friendo serve`.

**Minor:**
- "Open admin" links always point at the clearnet `sub.<base>`. That's acceptable.
- Cookies aren't `Secure` over plain-HTTP onion. The "is this HTTPS?" check is copy-pasted in
  five places (`requestIsHTTPS`, `secureRequest`, `requestOrigin`, `baseURL`,
  `redirectToApex`). One shared helper that also counts `.onion` as secure is a small
  cleanup.

## Open decisions

1. **Network scope for the first cut:** onion *alongside* the subdomain (recommended), or
   onion-only from the start?
2. **Key portability:** can an owner download their onion key and move the address off the
   network, in the spirit of "publish anywhere"? That means a guarded
   `friendo pull --onion-key`.
3. **Laptop `tor`:** require it installed (simplest), or auto-download the Tor Expert Bundle?
4. **Visitor actions over onion:** anonymous posting and the drop box attract spam over Tor.
   Should onion visitors get their own stricter limit, or a per-site switch?

## Verification (when built)

**Unit tests**, with `httptest` through the onion listener:
- `Host: localhost` + `X-Friendo-Admin: 1` gets no open admin.
- Forged `X-Forwarded-For` / `CF-Connecting-IP` are stripped.
- OTP echo is off.
- A non-onion Host is refused.
- The onion lookup routes to the right site.
- `tor` sits behind a small interface, so these tests use a fake.

**Opt-in integration test** (`FRIENDO_TEST_TOR=1`): start a real tor, publish an onion, and
fetch it through tor's SOCKS port.

**Manual checks:**
- `friendo serve --onion` in `testsite/`, then open the address in Tor Browser.
- `curl --socks5-hostname 127.0.0.1:9150 -H 'Host: localhost' -H 'X-Friendo-Admin: 1'
  http://<addr>.onion/_/api/...` must be refused.
- Run a local network with `./dev.sh` and `FRIENDO_TOR=1`, then `friendo deploy --onion`.
  The onion should load in Tor Browser and `sub.localhost` should still work.
