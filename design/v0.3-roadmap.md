# friendo v0.3 — roadmap (draft)

Builds directly on the shipped **v0.2 tag**. v0.2 got the feature surface *wired* —
auth/roles, community (comments/reactions/polls/channels/locations/media), sync,
and a 155-step parity harness — and made it *safe to run publicly*. v0.3 is the
**consolidation release**: it closes the gap between "the feature is shipped" and
"the feature is solid, honest, and covered," so that everything already in the
product genuinely works end-to-end before we take on the big 0.4+ bets.

**Scope theme: consolidation → 1.0.** No new marquee surface. Instead: finish the
half-wired parts of what already exists, make the markup for every feature
*intuitive*, grow test coverage past the REST API, and clear the coherence nits a
novice would trip on. The desktop editor, custom domains, and platform-operator
maturity are explicitly deferred to 0.4+ (below).

> **A note on server/client parity.** Parity is a *means*, not the goal. Some
> features are legitimately client-side-only — realtime chat and interactive maps
> only make sense in the browser, and galleries may too if a server-side render is
> disproportionately hard. The goal is **intuitive markup**: a novice drops in one
> obvious tag and it does the right thing, whether that resolves in the template or
> in a Web Component. We wire a feature server-side only where the content genuinely
> benefits (SEO, no-JS reads) — not as a blanket rule.

## North star

friendo's identity is *"your site is a folder — one UI, two runtimes, identical
behavior,"* aimed at **novice developers**. v0.2 proved that invariant for the REST
API and the data layer. A credible **1.0** additionally means:

1. **Every shipped feature has intuitive markup** — a novice can add any feature to
   a page with one obvious tag or helper and it just works. Where the content
   benefits from a server-side read (comments, reactions, polls, galleries) the
   template renders it directly; where the feature is inherently interactive (chat,
   maps) a `<friendo-*>` component owns it. Either way the author's markup is simple
   and consistent — no feature is a dead end because "you'd have to write JS."
2. **Every shipped feature is covered** — the parity guarantee is *tested* through
   the render layer and the CLI flow, not just the REST API.
3. **No dead ends for a novice** — file-based authoring, community data, and the
   admin UI tell one honest story with no stubbed switches or unbuilt widgets that
   look wired but aren't.

v0.3 is the step that makes (1)–(3) true for the *existing* surface. It does **not**
require the editor, custom domains, or bulk rollout — those are 1.0-adjacent bets,
not consolidation.

## Tier 0 — Server-side community content (where it earns it)

Comments, reactions, and polls are **content** — they benefit from a server-side
read (SEO, no-JS visitors, "view source" honesty). Today they render only via the
SDK Web Components, so a template author who wants approved comments in their page
markup has to ship JS. This is the community data that genuinely *should* be
renderable server-side. (Realtime chat/channels and interactive maps are the
opposite case — they stay client-side by design, see the parity note above.)

- **Server-side template relations** — expose approved/public community data in the
  render context of both engines: `{{ post.comments }}`, `{{ post.reactions }}`,
  `{{ post.poll }}` (and the by-slug front-matter poll). This needs a **lazy-load
  mechanism** in both template engines (Pongo2 + the edge regex engine) so a
  relation only hits the DB when a template references it — matching behavior, not
  just matching output.
- **Intuitive markup is the deliverable** — the template form (`{{ post.comments }}`)
  and the component form (`<friendo-comments>`) should feel like two spellings of
  the same idea, so a novice can pick either without surprise.
- **Render parity for the relations** — the harness gains a render-layer case per
  relation (empty, populated, moderation-filtered) asserting byte-identical output
  across runtimes. This is the first real render-layer parity coverage (see Tier 2).

*Why Tier 0:* it's the community data most worth reading without JS, and wiring it
also builds the lazy-load render plumbing the rest of 0.3 leans on. Chat and maps
are deliberately *not* in scope here — pushing them server-side would be effort
against the grain.

## Tier 1 — Finish file-based authoring (galleries / page bundles)

The media plumbing shipped in v0.2 (per-record upload, binary-safe asset push,
`files`-row sync), and the content importer already treats a `content/blog/my-trip/`
folder as a page bundle for slug purposes. The missing last mile:

- **Auto-attach page-bundle images** — importing `content/blog/my-trip/index.md`
  with sibling images creates `files` rows attached to that post (reusing the
  shipped upload/sync path, so they deploy byte-identical).
- **A gallery render helper** — intuitive markup for dropping the attached images
  into a page. Prefer a server-side `{{ post.gallery }}` (galleries are static
  content, so a template render is natural); if a server-side render turns out
  disproportionately hard, an SDK `<friendo-gallery>` is an acceptable fallback —
  the bar is *intuitive markup*, not mandatory server-side. Decide during
  implementation.
- Parity coverage for whichever path lands (import → attach → render/serve → sync).

*Why Tier 1:* it completes file-based authoring (the "your site is a folder" pitch)
without new primitives — it's assembly of existing plumbing, so it's lower-risk than
Tier 0 but higher-value than the Tier 3 niceties.

## Tier 2 — Grow coverage past the REST API

v0.2's harness is 155 REST-level steps + a render *smoke*. To call parity *proven*
for 1.0, two layers still need real coverage:

- **Render-layer parity suite** — promote the smoke to a first-class suite: nested
  same-tag loops, every filter, `forloop.*` counters, `escapeHtml` edge cases, and
  the Tier 0/Tier 1 relations. Byte-diff both engines. (This is the render-divergence
  guardrail from v0.2 made durable rather than smoke-tested.)
- **CLI flow coverage** — an end-to-end CI check of `deploy`/`push`/`pull` against a
  running runtime (init → push → pull → assert round-trip), the one flow with zero
  automated coverage today.
- **SQL statement-splitter robustness** — harden the schema/migration splitter (the
  known comment-line fragility) and cover it, so a schema edit can't silently drop a
  `CREATE TABLE`.

## Tier 3 — Novice-facing polish

Last-mile coherence — small, self-contained, each closes a "looks wired but isn't":

- **Persona switcher UI** — the accounts→authors split (one account, many profiles)
  is in the model but unexposed; add the switcher so authoring-as-persona is real.
- **`<friendo-map>` SDK component** — the locations API ships; add the map widget so
  geo-tags are renderable, matching the Tier 0/1 "server-side + client-side" pattern.
- **Per-member comment rate limiting** — the remaining Phase 3e hardening deferral;
  reuse the existing limiter pattern.

## Deferred to 0.4+ (documented, not dropped)

These are the **1.0-adjacent big bets** — deliberately out of the consolidation
release so 0.3 stays focused and shippable:

- **Phase 2 desktop editor** (Tauri WYSIWYG) — the largest novice-facing bet; an
  independent track. Form-factor (desktop vs in-browser) is itself an open decision.
- **Customer custom domains** (`friendo.toml deploy.domain` → Cloudflare for SaaS).
- **Platform-operator maturity** — an operator role + bulk runtime rollout across all
  sites (redeploy is per-site/owner-only today), plus provisioning hardening
  (`SITE_NAME` binding, subdomain validation).
- **`pull --community` snapshots.**

## Cross-cutting

The consolidation thesis in one line: **every shipped feature has intuitive markup
and is covered at every layer it actually runs.** Two guardrails carry it:

1. A **render-layer + CLI parity suite** (Tier 2) so the "identical behavior"
   invariant is proven through templates and the deploy flow, not just REST — for
   the features that *do* run in both places.
2. The **intuitive-markup rule** (Tier 0/1/3): every feature is reachable from a
   novice's page with one obvious tag or helper. Server-side where the content earns
   it (comments, reactions, polls, galleries); a `<friendo-*>` component where the
   feature is inherently interactive (chat, maps). Client-side-only is a legitimate
   choice — a *dead end that needs hand-written JS* is not.
