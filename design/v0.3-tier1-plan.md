# v0.3 Tier 1 — galleries / page bundles (execution plan)

Sequenced plan for Tier 1 of [v0.3-roadmap.md](v0.3-roadmap.md): finish file-based
authoring so a **page bundle** (`content/blog/my-trip/index.md` + sibling images)
auto-attaches its images to the post, and a template renders them with intuitive
markup — `{% for img in record.gallery %}`.

**No new primitives** — this assembles plumbing that already ships:
- Page-bundle *slug* parsing already exists ([content.go routeFor](../runtime/go/content/content.go#L163)).
- Per-record media rows (`files` table), the `/assets/*` static handler (disk / R2),
  binary-safe asset push, and `files`-row sync (`push --data`, carries `field`) all
  shipped in v0.2.

## Design (verified in code)

- **Import (Go, build-time only).** When `content.Import` upserts a page-bundle
  record it also imports the folder's images. Each image is copied to
  `assets/galleries/<collection>/<slug>/<filename>` — under `assets/`, so the
  existing static handler serves it and `readAssetsAsJSON` pushes it with no new
  wiring — and gets a `files` row: `record_type="post"`, `record_id=<post id>`,
  `field="gallery"`, `r2_key=assets/galleries/...`.
- **Deterministic ids.** The post id is already deterministic (`contentID` =
  sha256(collection,slug)). Gallery file ids follow suit: `DeterministicFileID` =
  sha256(record_id, filename)[:24]. So re-import and re-push **upsert in place**
  rather than duplicating — the same idempotency guarantee records already have.
- **Reconcile on re-import.** Each build clears the bundle's managed asset dir and
  its `field="gallery"` rows for that record, then re-imports the current set — so
  deleting an image from the folder removes it locally. (Removing it from an
  already-deployed remote is the same additive-push limitation media uploads have
  today; noted, not solved here.)
- **Render (both runtimes).** The single-record context gains `record.gallery` — the
  post's `field="gallery"` files, each `{id, url, mime, size, ...}` — attached right
  where Tier 0 attached comments/reactions/poll. Edge has no import path; it renders
  from the synced `files` rows + R2 bytes.

## The contract

| Key | Value |
|---|---|
| `record.gallery` | list of the post's gallery images, oldest first: `{id, record_type, record_id, field, url, r2_key, mime, size, created}` (empty list if none; `url` = `/` + `r2_key`) |

Intuitive markup: `{% for img in record.gallery %}<img src="{{ img.url }}">{% endfor %}`.

## Steps

1. **data.go** — `ListFilesByField`, `DeleteFilesByField`, `DeterministicFileID`.
2. **content.go** — `importGallery` in the `Import` loop for page-bundle records
   (copy images under `assets/galleries/...`, reconcile `field="gallery"` rows).
3. **server.go / index.js** — rename the Tier 0 `attachCommunityRelations` →
   `attachRecordRelations` and add `record.gallery` (Go: `ListFilesByField`; edge:
   the same `field='gallery'` files query).
4. **testsite** — add a `content/blog/*/index.md` page bundle with a couple of small
   images; render `record.gallery` in the blog template.
5. **Verify** — build + import (Go), render + diff the gallery across both runtimes
   after a push (as in Tier 0); confirm re-import is idempotent (stable ids).

## Out of scope (noted)

- **`<friendo-gallery>` SDK component** — server-side rendering is the natural fit
  for a static image list (intuitive markup, no JS), so per the roadmap's parity
  note the component is an optional nicety, deferred unless a client-side need shows
  up.
- **Remote deletion of removed images** — additive-push limitation shared with media
  uploads; a `pull`/`push --prune` pass is post-1.0.
- Orphan-byte cleanup for images removed from a bundle on the *remote*.
